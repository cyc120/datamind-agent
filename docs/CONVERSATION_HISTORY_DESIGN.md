# 对话历史（History）交互设计

本文件只回答一件事：**怎么把「历史对话」做成主流 AI 应用那种可发现、可找回、可命名的样子。**

结论先说：当前不是「没有历史」——`GET /v1/sessions` 与侧栏那块列表一直在跑（开发库里 69 条会话、
全部属于本机回环身份 `user-local-admin`）。缺的是**入口形态**与**行内动作**：历史只以一块常驻列表
存在，没有显式入口、不能改名、不做时间分组、不能被深链指向。本文件给出分三批的改法，每批都能独立
验收，且**不改任何接口契约**（P1 的可选增强除外，它单独标注）。

> **实施状态（2026-10-13）**：**P0 四项已落地**（`SideNav.vue` / `useSessions.ts` / `MainPage.vue` /
> `LandingPage.vue` / `RunsPage.vue`），并在无头 Chrome 里真渲染验证过（20 行会话 + 三个时间分组 +
> 深链直达 + 落地页零会话泄漏）。P1（搜索命中片段）与 P2（置顶、独立历史页）**未做**，见 §4/§5。
>
> **另发现并修复两个前置缺陷**（它们才是「看不到对话历史」的真实原因，见 §0.1）：侧栏历史区被
> flex 压成 **4px**、`overflow: hidden` 又把底部裁掉；`⋯` 菜单在列表底部几行被滚动容器裁掉，
> **真实鼠标点不到**。两者都已修复，并新增可复跑的浏览器级验证
> [scripts/verify_frontend_layout.py](../scripts/verify_frontend_layout.py)。

## 0.1 两个真实缺陷（修复前实测数据）

这两条不是设计取舍，是缺陷。它们的共同点是：**元素都在 DOM 里**，所以源码断言、`--dump-dom`
的 DOM 树、甚至「元素存在/有文字」的检查**全都是绿的**——只有量几何、做命中测试才看得见。

### 缺陷一：历史区被压成 4px，用户根本看不到历史

| 视口 | `.sessions` 高度 | 「历史对话」标题可见 | 完整可见行 |
| --- | ---: | --- | ---: |
| 1440×900 | **4px** | 否（被 `overflow-y: auto` 裁掉） | **0** |
| 1280×720 | **4px** | 否 | **0** |
| 800×600 | **4px** | 否 | **0** |

根因：侧栏固定高度块合计约 880px（主导航 449 + 底部状态区 298 + 顶部与「新对话」约 80 + 间距 56），
比常见视口还高；`.sidenav` 是 `overflow: hidden`，`.sessions` 又是 `min-height: 0`。
flex 的收缩压力全落在唯一「可缩」的历史区上，于是它归零，底部状态区被裁掉且永远够不到。

修复：`.sessions { min-height: 216px }`（≈标题 + 搜索框 + 3 行）、`.sidenav` 改为 `overflow-y: auto`
（空间不够时整体滚，而不是压没中间、裁掉底部）。

### 缺陷二：列表底部的 `⋯` 菜单点不到

`.sess-menu` 是行内 `position: absolute`，而列表容器是 `overflow-y: auto`。靠近列表底部的行，
菜单向下展开被裁掉：`document.elementFromPoint(菜单项中心)` 返回的是 **`aside.sidenav` 本身**，
`Input.dispatchMouseEvent` 真实点击**没有任何反应**（程序化 `.click()` 会绕过命中测试，测不出来）。

修复：打开菜单时量一次几何，下方放不下且上方放得下就翻到行上方（`.sess-menu.is-up`）。

### 缺陷三（顺带）：标题与搜索框会被列表滚走

标题和搜索框原本和列表在同一个滚动容器里，列表一往下滚它们就跟着滚没了——找一个旧会话得先
滚回顶部才能搜。修复：拆成两层，`.sessions` 不滚（标题 + 搜索框钉住），只有 `.sess-body` 滚。

### 缺陷四：折叠「收不起来」——内容藏了，空间没还

为缺陷一加的 `min-height: 216px` 是为**展开态**定的，但它对折叠态一样生效：折叠后只剩标题一行，
那块 216px 空白照样占着，下面的导航不上移，看起来就是「点了没反应 / 收不起来」。
实测：折叠后 `.sessions` 仍是 **216px**、导航 `top` **350 → 350**（一点没动）。

修复：模板给容器挂 `.is-collapsed`（CSS 不知道 Vue 状态），折叠态 `min-height: 0; flex: 0 0 auto`。
实测折叠后 **22px**、导航 `top` 350 → **156**（真的收回 194px），再点一次恢复 216px / 20 行。

**这条也暴露了旧判据的漏洞**：原来只断言「搜索框消失 + `aria-expanded=false`」——那两条在**有
缺陷的版本上依然全绿**（变异实测）。所以现在的判据是几何性的：折叠后高度必须回落、下方导航必须
上移；并且「再点一次完整恢复」要同时查搜索框、高度与会话行数。

### 为什么新增了浏览器级验证脚本

以上四条**只有真实浏览器 + 几何 + 命中测试**能发现。所以新增
[scripts/verify_frontend_layout.py](../scripts/verify_frontend_layout.py)：用无头 Chrome 在 3 档视口量
高度、发真实鼠标事件、做 `elementFromPoint` 命中测试，共 **26 项判据**；没有 Chrome 时**明确跳过**
（不伪装成通过）。两次**变异验证**：① 把展开态 `min-height` 改回 0 → 9 项变红；
② 删掉 `.sessions.is-collapsed` 规则 → 折叠两条几何判据变红（而旧的「搜索框消失」判据**仍然绿**，
说明新判据不是空转）。

**边界（先说清楚）**：会话**不是多轮记忆**。本设计只改「组织与找回」，不改变
`/v1/chat` 的 `history` 契约——向模型提供历史仍然完全由客户端每次请求自带
（见 [会话接口契约](SESSIONS.md) §0 与 [多轮上下文契约](MULTI_TURN.md) §2）。

## 1. 现状核对：哪一件已有、哪一件真的缺

| 能力 | 现状 | 依据 | 与主流 AI 应用的差距 |
| --- | --- | --- | --- |
| 列表取数 | **有**（`limit+1`/`has_more`，最近活动优先） | `datamind/sessions.py::listing` | — |
| 搜索 | **有**（服务端命中标题 + 任意 `question`/`answer`，250 ms 防抖） | `sessions.py` §6；`SideNav.vue:157` | **看不见为什么命中**（行里显示的是「最近一次提问」，与搜索词无关） |
| 新建对话 | **有**，且 `Ctrl/⌘ + K` 是真实现的（不是假提示） | `SideNav.vue:216,250-261` | — |
| 重命名 | **后端 `PATCH` 与组合式函数的 `rename()` 都已实现，界面零入口** | `sessions.py::rename`；`useSessions.ts:341`；`SideNav.vue` 根本没解构 `rename` | ⚠️ **最不像主流应用的一处** |
| 删除 | **有**（两步确认，后端是软删） | `SideNav.vue:305-330` | 无「回收站」（软删已具备，缺恢复入口） |
| 时间分组 | **无**（一条平铺列表） | `SideNav.vue:283-337` | 主流应用都是「今天 / 昨天 / 前 7 天 / 更早」 |
| 可见预览 | **无**。`last_question` 只出现在 `title` 悬浮提示里 | `SideNav.vue:299-303`（行内只有标题 + 相对时间 + 轮数） | 缺一行摘要 |
| 深链到某个会话 | **无**。只有 `localStorage` 记住上次；`?q=&mode=` 是**提问**深链 | `MainPage.vue:318-329` | 不能收藏、不能从别处跳进一个具体会话 |
| 首页入口 | **无**（落地页没有侧栏，也没有任何指向历史的入口） | `LandingPage.vue`；`SideNav` 只被 8 个应用页引入 | **从首页到历史是断头路** |
| 置顶 / 收藏 | **无**（需要新列） | — | 可选 |
| 独立历史页 | **无** | — | 可选（大屏左列表右预览） |

顺带一个**已经存在但被浪费**的交叉入口：`/runs`（运行记录）已经把 `conversation_id` 显示出来，
但是**纯文本、点不动**（`RunsPage.vue:151-152,167`）。只要 P0-4 的深链一落地，「从运行记录跳进
它所属的会话」就自动成立——这是本设计里性价比最高的一条。
**实现取舍**：入口没有做在行内那个「会话 xxx」徽章上，而是放在**展开后的详情**里的
「打开该会话 →」按钮——整行本身是 `<button>`（点开详情），`<button>` 里再嵌 `<a>` 是非法 HTML，
点链接还会连带触发整行的展开。

## 2. 目标形态

### 2.1 侧栏（主入口）

```
DM
┌──────────────────────────────┐
│  ＋ 新对话            ⌘K      │
├──────────────────────────────┤
│  历史对话                     │   ← 文案从「会话」改为「历史对话」
│  ⌕ 搜索对话…                  │
│  ── 今天 ──                   │   ← 时间分组（纯前端，数据已在手）
│  ▸ 2024年每个大区销售额…   ⋯  │   ← 悬停才出现 ⋯ 菜单（重命名 / 删除）
│    14:32 · 3 轮               │
│  ▸ 退款条件是什么          ⋯  │
│    11:05 · 1 轮               │
│  ── 昨天 ──                   │
│  …                            │
│  [ 加载更多 ]                 │
└──────────────────────────────┘
```

要点：**列表本身仍是常驻的**（不藏进抽屉）——主流 AI 应用也是这样，历史不该需要「先点一个按钮
才能看见」。所谓「加一个历史按钮」在这里的正确解法是**给这块区域一个显式标题与入口语义**，
而不是把列表挪到一个按钮后面。

### 2.2 一行里放什么

| 位置 | 内容 | 依据 |
| --- | --- | --- |
| 主文案 | 会话标题（自动命名 = 首轮提问前 40 字） | `sessions.touch()` |
| 副文案 | 相对时间 + `run_count` 轮 | 后端已返回 `updated_at`/`run_count` |
| 悬停动作 | `⋯` → 重命名 / 删除（删除保留现有两步确认） | 复用 `rename()` / `remove()` |
| 激活态 | 高亮 + 主区显示该会话 | 现有 `is-active` |
| 右键/长按 | 暂不做 | — |

**为什么把删除从常驻 `✕` 收进 `⋯`**：现在每行右侧常驻一个 `✕`，视觉噪声大且容易误触（已有两步
确认兜底）。收进菜单后，行内只在悬停/聚焦时出现一个动作按钮，键盘用户仍可 `Tab` 到达。

## 3. P0：先做这四件（改动小、都能验收）

### P0-1 显式入口与命名

* 侧栏区块标题「会话」→「历史对话」（**只改界面文案**；接口与文档仍叫 session/会话，契约不动）。
* 标题右侧加一个**折叠开关**（`⌄`/`⌃`）：折叠后整个历史区只剩标题一行，把空间让给下面的导航；
  折叠状态存 `localStorage`（沿用 `datamind.` 前缀，如 `datamind.sessions.collapsed`）。
  默认**展开**——主流 AI 应用的历史是默认可见的，折叠是给「这一屏只想来问问题」的用户准备的。
* 导航「工作台」组里再加一个**动作型**条目「历史对话」（`action: 'history'`）：点它 = 回到工作台 +
  展开历史 + 聚焦搜索框。**刻意不给它 `to`**：它和「问数与问答」同为 `/app`，两个条目同时高亮会
  让人以为有两个页面（有测试钉住这一点）。列表本身**不藏进这个按钮**——历史仍默认可见。
* 落地页顶栏加一个「历史对话」按钮 → `router.push('/app')`，并带 `?panel=history`；
  `MainPage` 挂载时若发现该参数就**展开历史区并聚焦侧栏搜索框**，然后清掉参数（用 `router.replace`）。

> **隐私红线**：落地页是**对外页面**，绝不在它上面渲染任何会话标题或摘要（哪怕本机回环能取到）。
> 那里只放一个跳转按钮。

### P0-2 重命名（复用已有实现，零后端改动）

* `SideNav` 解构 `useSessions().rename` 与 `busy`；
* 行内进入编辑态：标题变成输入框，`Enter` 保存 / `Esc` 取消 / 失焦保存；
* 校验口径与后端一致（空白 → `SESSION_TITLE_REQUIRED`，>200 字 → `SESSION_TITLE_TOO_LONG`），
  这些中文提示 `useSessions.ERROR_TEXT` 里**已经有了**，不需要新写；
* 成功后 `mergeSession` 已负责把它挪到列表最前，侧栏无需额外处理。

### P0-3 时间分组

* 纯前端：`rows` 已有 `updated_at`，按本地时区切成 **今天 / 昨天 / 前 7 天 / 更早** 四档；
* 搜索态**不分组**（搜索结果按相关度看更自然，而我们的排序仍是 `updated_at DESC`——这一点要
  在界面上说明，不能假装是相关度排序）；
* 分组标题不参与行点击，`role="presentation"`。

### P0-4 深链 `#/app?session=<sess-id>`

* `MainPage` 挂载时：`route.query.session` 匹配 `^sess-[0-9a-f]{24}$` 就**优先于** `localStorage`
  的 `activeId`（当前只有后者，见 `MainPage.vue:318-329`）；
* 挂载后 `router.replace` 清掉参数，避免刷新时反复覆盖用户手动切走的会话；
* 顺带在 `/runs` 的**展开详情**里加「打开该会话 →」（`RunsPage.vue::openSession`，见 §1 末段的
  实现取舍）；
* 这一步让「运行记录 → 具体会话」和「收藏/分享本机会话」同时成立。

## 4. P1：搜索体验（需要一次小的后端增强，可选）

**问题**：搜「退款」时，服务端是按 `runs.answer` 命中的，但列表行显示的是 `last_question`
（最后一次提问，可能完全无关），悬浮提示也一样。用户会以为「搜出来的都不是我要的」。

**方案 A（纯前端，零后端）**：搜索态下把副文案换成「命中在历史问答中」，或在行的 `title` 提示里
写明「标题未命中，命中在问答正文」。诚实，但信息量仍然接近零。

**方案 B（推荐，后端 +1 个字段）**：`listing` 在**有 `q` 时**额外返回 `match_snippet`：

```jsonc
{ "session_id": "...", "title": "...", "run_count": 3,
  "last_question": "...",
  "match_snippet": { "field": "answer", "text": "……七天无理由退款的条件是……", "run_id": "run-…" } }
```

* 取值：`LEFT JOIN LATERAL` 取**第一个命中的 run**，对命中字段截取命中位置前后各 ~40 字符，
  折叠空白；不命中任何 run（只命中标题）时 `field="title"`。
* 成本：只在 `q` 非空时多一个相关子查询；这条路径刚做过计划优化（见 §SESSIONS.md §6.1），
  实测选择性词 14.3 ms，多一次截取不改变量级。
* 隐私：`match_snippet` 只从**请求者自己的会话**里取，与 `q` 的归属约束同一条 SQL。
* **不做**：把整段命中原文返回（那就是把聊天正文灌进列表接口，破坏 `detail`/`results` 的分工）。

## 6. 明确不做（以及为什么）

1. **不做跨设备同步**：会话存在本机 `datamind_meta`，没有账号体系级别的服务端存储（`SESSIONS.md` §8）。
2. **不做「历史作为模型上下文」**：会话≠记忆（`SESSIONS.md` §0）。多轮仍由客户端自带 `history`。
3. **不在落地页列会话**：对外页面不渲私有内容（见 P0-1 的红线）。
4. **不做回收站**：后端已是软删（`deleted_at`），但「已删除会话」列表 + 恢复接口是一套新契约，
   本轮不夹带。
5. **不做历史正文的向量检索**：几十到几千条量级用 `ILIKE` + 惰性探测就够；引入 embedding 检索
   要新增索引与一致性维护，收益不成比例。
6. **不承诺搜索结果按相关度排序**：排序恒为 `updated_at DESC`（最近活动优先），界面上如实说明。
