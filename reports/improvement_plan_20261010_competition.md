## 0. 一页结论

| 项 | 现状（审计） | 本计划目标 | 主要来源 |
|---|---:|---:|---|
| 初赛内部估分 | 69 | **85–87** | E7 +5、E8 +5、E10 +2、E11 +2、E4 +2（并守住 E1/E2/E5/E6 不因新版本失效） |

| 高级加分 | 0 | **8–12（有条件）** | 单一贡献：「版本化的跨源证据绑定 + 可控修复」；先做阻断实验，再决定是否申报 |
| 交付合规 | 缺 Word/PDF/PPT/ZIP | 成套齐备 | WP9 + WP10 |

**计划主线只有一句**：把已有的「可解释链路 / 受控查询 / 版本与权限 / 缺口如实声明」从工程机制，转成**评委可复现的跨源问答证据**，并用一个可度量的创新点把它串起来。

**创新的落点不是新模型，而是一个新的度量与机制**：
> 跨源问数最容易犯的错，不是查不到，而是**把证据绑错了对象、版本、单位或时间口径**后仍然给出高置信度答案。
> 本项目把「实体/版本/单位/口径绑定」提升为一等公民（Evidence Binding），并给出可复现的度量（绑定准确率、**错误绑定率**、冲突检出率、误修复率）与可控修复上限。

这条主线同时喂饱三个最难的分项：F1（跨源）、F8（中级任务数量，B2/B8 复用同一证据层）、F9（改进质量，因为可以和「普通流水线」做对照消融）。

## 1. 制定原则（避免把工作做成无效分）

1. **不新增「又一个大模块」，只做闭环与证据**。审计已指出差距从「缺组件」转为「缺闭环与独立证据」。
2. **每个工作包交出四件套**：可复现命令 + 机读 JSON 报告 + 一页中文结论（可直接进比赛文档）+ **保留的失败样本**。
3. **一项能力配一项度量**。E1/E2 是每题计分，E5/E6/F4/F5 是比率指标，必须分别设计验收，不用一个通过率解释所有分数（审计 §4 明确警示）。
4. **不伪修**。任何「提升」都不得以放宽断言、移动分母、把拒答移出统计来达成；正向对照与反向对照同时写。
5. **新代码不得改变既有行为**：不传 history / 不选跨源时不改提示词与结果（沿用 0.39.0 已有的「逐字节不变」纪律），每次改动都跑隔离回归并同步分母。
6. **证据先行于排版**。每完成一个实验就产出一页结论卡；最终 Word/PDF 由这些卡片拼装，而不是最后从零写（审计 §10 建议）。

## 3. 创新点设计（可直接写进《突破与创新性自述》）

### 3.1 核心贡献（单一贡献，一句话可陈述）

> **版本化证据绑定的跨源问数（Version-Bound Evidence Binding）**：系统不直接生成跨源结论，而是先生成一张带类型的**证据图**（数据行 / 文档块 / 测量 / 规范条款是节点；实体同一性、版本适用、单位等价、时间口径、数值支持、数值冲突是边），然后用**受控修复**在有限次数内消解冲突；无法消解时**同时展示双方证据并标记待裁决**，绝不自动选一个来源。

### 3.2 机制要点（都与现有代码对齐，不是另起炉灶）

| 要素 | 现有资产 | 本计划的增强 |
|---|---|---|
| 实体同一性 | `entity_aliases`（approved）参与 Schema 召回（`datamind/catalog.py`） | 抽出独立 `entity_binding`，跨 SQL 行与文档块共用一个规范实体 id，绑定必须回指原值 |
| 连接路径 | `Catalog.join_path()`（`datamind/catalog.py`） | 跨源 P4 多跳复用同一路径规划，跳数与证据边一起进解释 |
| 版本与单位 | 图纸/工艺版本、`industrial_rules.py` 的单位与版本核验、来源权威登记（migration 006） | 泛化为 `binding{entity_id, version, unit, time_scope, source_sha256}`，并作为**答案必填字段** |
| 冲突处理 | 工业规则「未登记权威时不选来源，保留双方原值」 | 升格为跨源通用裁决门 + `CONFLICT_UNRESOLVED` 稳定码 |
| 受控修复 | V-CAR 修复上限、`ablation.py` 的修复成功率/误修复率指标 | 跨源修复只看**绑定错误**（对象/版本/单位/口径），每次修复必须记账；新增**误修复率 ≤2%** 的硬门 |
| 可解释 | 事件流、回放、引用卡片、契约关系 | 证据图可视化：节点类型、边类型、绑定字段、冲突双方 |

### 3.3 可复现度量（这是加分材料真正缺的东西）

1. **绑定准确率** = 正确绑定到（对象 + 版本 + 单位 + 时间口径）的声称 / 全部带数值的声称。
2. **错误绑定率**（本计划的标志性指标）= 绑定错误却仍以 `confidence ≥ high` 输出的声称比例。目标：基线 → ≤3%。
3. **冲突检出率 / 误报率** = 同一来源相反值、跨版本不一致、单位不可归一化、时间范围不重叠四类，分别报 P/R。
4. **修复账本** = 尝试次数、成功率、**误修复率**、每次修复带来的延迟与 token 成本。
5. **对照消融**：`plain`（直接拼接 SQL 结果与文档片段让模型答）/ `bind_only`（绑定但不核验）/ `full`（绑定 + 核验 + 受控修复）三臂在同一冻结集上比较。**注意纪律**：V-CAR 现有的 16 例合成替身消融只能解释机制，不得当作本项的领先性证据（审计 §9）。

### 3.4 诚实边界（必须写进自述）

- 真实视觉大模型与本地权重对比**不可执行**（上游仅文本模型、无权重目录），因此不主张「多模态识别领先」。
- `plain` 臂若在同集上也接近满分，则本项只能申报「实用创新与转化价值」，不能申报「技术突破领先性」。
- 所有集为自建冻结集，报「相对提升 + 绝对数值 + 失败清单」，不外推为业界领先。

## 4. 工作包（WP）

排序按「提分收益 ÷ 工作量」，并标注依赖。**P0 = 必须做，P1 = 决定上限，P2 = 有时间再做。**

### WP1 冻结评测基线（P0，3–4 人日；依赖：无）

**问题（审计 §4/§7.1）**：历史 NL2SQL 14/14 与 RAG 10/12 来自更早代码和小样本，不能代表 0.39.0；且题库在 `evaluation_cases` 表里、冻结哈希只在部分 RAG 题上生效，证据链不自洽。

**做法**
1. 把评测升级为**append-only 评测登记**：`data/evaluation/registry/<suite>_v<n>.json` 内含 `suite_version / data_version / commit / model / prompt_version / cases[] / expected / digest`；已发布版本只增不改。
2. 题库入仓（不再只存数据库），seed 时校验「库内题面 == 仓内题面」，不一致直接失败（沿用 `scripts/eval_rag.py` 已有的对比式校验思路，扩展到全部 suite）。
3. 新增/补全子集：单表 ≥10、复杂（JOIN 3 表 + 聚合 + 嵌套）≥15、单文档 ≥12、多文档 ≥8、拒答/不可答 ≥6、鲁棒（错别字/口语简称/越权/空结果）≥10。
4. 结果报告统一 schema：逐题 `status / sql / gold / rows / citations / verdict / failure_reason`，并输出**总表**（准确率、拒绝率、失败分类计数）。

**交付物**：`scripts/eval_registry.py`（新）、改造后的 `scripts/eval_sql.py`/`eval_rag.py`、`reports/baseline_v1.json`、一页结论卡。
**验收**：一次命令产出全部子集报告；改动任一冻结题面则评测**拒绝运行**并给出 diff 码；报告含全部失败样本与原因。
**收益**：坐实 E1/E2/E5/E6，并消除「旧高分在新版本失效」的风险；同时为 E9 提供材料。

### WP2 跨源融合引擎 + 三种真实跨源问题（P0，6–8 人日；依赖 WP1）

**问题（审计 §5，最大扣分项 F1 = 0）**：`datamind/agent.py` 中 `route_for()` 仅用关键词命中 `cross_source`，随后**直接**返回 `ROUTE_UNSUPPORTED`；工业 13 条规则只覆盖「一份工艺文档 + 生产 SQL」的单一结构。

**做法**
1. 新模块 `datamind/cross_source.py`：范围解析（源 + 文档集合）→ 证据图构建 → 绑定 → 核验 → 受控修复 → 答案（必带证据图与绑定字段）。路由层保持 fail-closed：未识别的跨源问法仍返回稳定码，绝不猜。
2. 新契约存储（新增 migration `019_evidence_graph.sql`；仓库现有迁移止于 `018_upload_claim_generation.sql`）：`evidence_nodes(run_id, node_type, ref, source_sha256, version, unit, time_scope)`、`evidence_edges(run_id, src, dst, edge_type, binding_type, confidence, evidence)`；边类型受 CHECK 约束（`entity_match/version_scope/unit_equivalent/time_overlap/supports/conflicts`）。
3. 落地四种任务结构（前三项对应官方「≥3 种」，第四项冲 8–10 分）：
   - **P1 SQL 结果驱动文档检索**：「2025 年华东销售额最高的品类是哪个？该品类的渠道经验怎么说？」→ 需给出数值 + 文档解释 + 双证据。
   - **P2 文档规则驱动 SQL 筛选**：「按《售后服务与退款管理制度》的时限，找出超过该时限仍未完成的退款单」→ 文档取阈值，绑定单位/时间/对象后再查库。
   - **P3 跨源异常核验与冲突呈现**：「A102 工序 30 的实测温度与工艺规范的偏差是否超限，与质检报告是否一致？」→ 需呈现来源冲突、适用版本与不能裁定的原因。
   - **P4 复杂多跳（争取档）**：SQL 异常 → 实体/版本 → 规范条款 → 说明材料，一跳一证据边，跳数可数、可回放。
4. 裁决门复用 `source_authority_rules`：**未登记权威 → `CONFLICT_UNRESOLVED` + 双方原值 + 待裁决标记**；已登记权威才允许按规则收敛。
5. 前端：证据图卡片（节点/边/绑定字段/冲突双方）、跨源入口与范围展示。

**交付物**：`datamind/cross_source.py`、migration 019、`scripts/eval_cross_source.py`、`data/evaluation/cross_source_v1.json`、前端卡片、一页结论卡。
**验收（写死）**：
- 三种结构各 ≥5 条冻结样例，**结构必须不同**（不是换三组输入），每条含期望答案、期望绑定字段、期望证据类型、失败边界。
- P1/P2/P3 通过率 ≥80%；**错误绑定率 ≤5%**；冲突类必须 100% 展示双方证据（宁可 `insufficient` 也不单选）。
- 负向对照：故意注入错版本文档 → 系统必须报版本不一致而非照答。
- 不改变非跨源路径的提示词与结果（逐字节比对断言）。
**收益**：F1 0→6（争取 8）、E3 巩固、F3 素材；并为 WP3 提供运行载体。

### WP3 创新点度量与对照消融（P1，3–4 人日；依赖 WP2）

**做法**
1. 构造**版本冲突陷阱集**（≥40 例，四类陷阱：同对象跨版本、单位不同/不可归一、时间口径不同、文档与库数值相反），先写期望再评测（沿用 CAD 冻结集的「先冻结标签后评测」纪律）。
2. 实现三臂消融 `plain / bind_only / full`，复用 `datamind/ablation.py` 的指标算术（零分母报 N/A，不用 0 冒充）。
3. 报告：绑定准确率、**错误绑定率**、冲突 P/R、误修复率、修复次数分布、延迟与 token 成本。

**交付物**：`data/evaluation/binding_traps_v1.json`、`scripts/eval_binding.py`、`reports/binding_ablation.json`、一页结论卡。
**验收**：三臂在同一冻结集同一环境跑完；`full` 臂错误绑定率相对 `plain` 下降 ≥50% 且绝对 ≤5%；**若达不到则本项降级为「实用创新」并相应下调加分预算**。
**收益**：高级加分举证（8–12 分区间）、F9 的对照材料。

### WP4 中级任务一：B3 澄清闭环验收（P0，2–3 人日；依赖 WP1）

**做法**：把「提出缺项 → 用户补充 → 消歧/补槽 → 完成查询」做成完整可演示闭环（含前端一次补充后直接完成，不需要重开对话）；冻结 ≥20 条澄清场景，统计**澄清成功率**、**不必要澄清率**、**平均澄清轮次**；把「不必要澄清」（本可直接回答却反问）作为独立失败项登记。
**交付物**：`data/evaluation/clarification_v1.json`、`scripts/eval_clarification.py`、前端补槽交互、一页结论卡。
**验收**：澄清有明确缺项字段与补槽结果；不必要澄清率 ≤10%；`NEEDS_CLARIFICATION` 语义在 API/前端一致。
**收益**：E8（5 分项之一做实）、F2 7→10。

### WP5 中级任务二/三：B2 可扩展要素提取 + B8 文档复杂度评估（P1，6–8 人日；依赖 WP1）

**B2（第三种任务，官方难题②）**
1. 选一个**未参与开发的领域**（建议：设备维保工单，或供应商质检单），只用现有元数据注册表加声明式配置。
2. 记录并公开成本：配置行数、标注样本数、**代码改动行数**（目标 0 行引擎改动）、原领域回归是否受影响。
3. 证明**不依赖大段 few-shot**：同一任务在「无示例 / 3 示例 / 10 示例」三档下比较，若收益差 ≤5 个百分点即证明不靠示例堆。

**B8（当前「未实现」，审计 §6）**

### WP7 多轮上下文与前端会话（P0，4–5 人日；依赖 WP1）

**问题（审计 §7.1）**：`datamind/agent.py:276` 仍按当前 question 路由；`sql_engine.py:796` 在生成前按当前 question 澄清/召回；`rag_engine.py:178` 按当前 question 检索。历史只在生成提示词里用到 → 「那上一年的呢？」「第二个产品呢？」可能在路由阶段就走偏。

**做法**
1. **路由前**生成结构化「本轮问题帧」：实体、指标、时间、数据库/文件范围、**用户本轮覆盖项**；范围继承必须显式（`inherited_from_turn`）并**继续走权限检查**（安全授权边界与语义上下文分离，不拼接历史）。
2. 会话范围存储为**请求内上下文 + 服务端可选的显式 session 记录**（不隐式继承权限、不越权扩大范围）；重开会话即清空。
3. 前端：连续聊天、当前范围可视、一键重开、澄清补充内联。
4. 冻结 **10 段 × ≥6 轮**对话集（指代、省略、纠错、换主题、澄清补充、权限变化各至少 1 段），报**逐轮正确率**与**整段全对率**。

**交付物**：`datamind/frame.py`（或 `sql_engine.frame_for` 扩展）、`docs/MULTI_TURN.md` 更新、`data/evaluation/multi_turn_v1.json`、`scripts/eval_multi_turn.py`、前端会话、一页结论卡。
**验收**：≥6 轮连续记录（真实模型），逐轮与整段双指标；权限变化轮必须拒绝而非继承；不传 history 时行为逐字节不变。
**收益**：E10 3→5、F2 7→10。

### WP8 效率与伸缩性证明（P1，4–5 人日；依赖 WP1）

**问题（审计 §7.2）**：`scripts/eval_scale.py` 的 retrieval 分支只跑 `_selected_rows`，不含召回+重排+生成；计时含导入与连接；无并发、无 SQL 侧规模。

**做法**
1. **SQL 侧 3 档**：1 千 / 1 万 / 10 万行（同 schema，生成器入仓），固定查询集。
2. **文档侧 3 档**：10 / 100 / 500 页，固定问题集。
3. **分段计时**：路由 / 召回 / 查询或检索 / 模型 / 首字 / 完整响应，冷启动与预热分开，报告 p50/p95。
4. **并发 1/2/4/8**：成功率、每秒完成数、峰值内存。
5. **复杂度分析 + 一处真实优化**：给出各模块复杂度，指出瓶颈（候选扫描/重排或块定位查询），做一次优化前后对照并报差值。已知规模点中 CAD 后两档为 `partial`（上限 2000 块）——必须如实标注为**受限输出路径测量**。
6. 模型不可用时**只报工具链测量**，完整问答时延留空，不用 mock 延迟充数。

**交付物**：改造后的 `scripts/eval_scale.py`、`reports/scale_v2.json`、`docs/PERFORMANCE.md`（复杂度 + 瓶颈 + 优化）、一页结论卡。
**验收**：≥3 档 × ≥2 路径 × 并发矩阵齐备；每个数字有环境说明；优化对照可复现。
**收益**：E7 0→5、F6 1→5。
